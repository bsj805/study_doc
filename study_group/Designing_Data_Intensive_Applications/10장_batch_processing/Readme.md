### 유닉스의 철학

연쇄 명령을 사용해 쉽게 로그 파일을 분석할 수 있게 한다. 

유닉스 파이프 개발 원리
- 각 프로그램이 한 가지 일만 하도록 작성하라. 
- 새 작업은 기능 추가하지말고 새 프로그램을 작성해라 
- 모든 프로그램 출력은 다른 프로그램의 입력으로 쓰일 수 있게 해라 
- 소프트웨어를 빠르게 써볼 수 있게 설계하고 구축해라 
- 프로그래밍 작업을 줄이려면 도구를 사용해라. 

동일 인터페이스 (호환 가능한 인터페이스 쓰기) 가 중요하다. 

유닉스에서는 파일이라는 인터페이스로 통신한다. stdout, stdin 조차 다 파일. 

그리고 그걸 다 ascii로 읽어들일 수 있게 한다. 

동일한 데이터 모델인 DB도 한쪽에서 다른쪽으로 가는게 쉽지 않다. 

#### 유닉스 철학 - 투명성

진행 상황 파악이 쉬움 

파일에 쓴다음에 다시 읽어도 똑같이 사용가능.

다만, 단일 장비에서만 실행되니 하둡이 그 해결책 

### skewed join
핫키 (linchpin object) 는 같은 맵키로 데이터가 엄청 들어온다. 

해결책으로 

1. pig - hot key에 조인되야하는 입력들을 핫 키가 전송된 모든 리듀서에 복제한다 (거꾸로하기)
2. Hive - hot key 관련 레코드를 별도 파일에 저장. 해당은 리듀서에서 모아서 처리하기보단, mapper 단에서 다 처리해버리기. 
  - 메모리에다가 join해야할 데이터를 다 올려둬서 reducer로 가서 모일 필요가 없다. 

### 왜 map reduce + DB 조회 안할까? 

- 모든 레코드마다 네트워크 요청하면 너무 느림 
- 맵 리듀스 작업 == 병렬 task 처리. DB가 과부하 
- 성공한 경우에만 출력 생성을 보장. 외부와 소통하면 side effect 만들 수 있음

그래도 schema on read 방식을 채택해서 reader 설계에 따라 자유로운 파일 형식 

## MR의 문제 

매번 중간 결과물 파일을 생성한다. 2개의 task로 나눠져 있으니까. 

Spark,Tez, Flink 같은건 하나의 워크플로우로 간주한다. 이들은 데이터 플로우 엔진이라고 부른다. 

여러 operator를 결합할 수 있다. 

- 필요없는 맵 태스트 없다
- 정렬은 필요할 때만 
- 스케줄러가 어느 데이터 어디 필요한지 알아서, 데이터 지역성 최적화 
- JVM 재사용 가능하다. 맵리듀스는 매번 JVM 재구동. 

다만 내결함성이 없어지는데 (중간 상태 파일 저장), 재계산 기능은 만들어져 있다. 

### 프리글 처리 모델 (Pregel 모델)

bulk synchronous parallel, BSP 를 사용하면 개별 node에서 함수를 호출해 해당 node에 데이터를 보낸다. 

프리글은 iterative로 그래프 문제를 풀기 위함.
