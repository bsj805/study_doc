
복잡하지만 잘 작동하는 시스템은 예외 없이 간단하지만 잘 작동하는 시스템으로부터 발전한다. 

배치 처리의 출력은 파생 데이터 형태이다. 즉, 필요시 일괄처리 다시 수행하면 재생성 가능함. 입력이 언제 끝나는지 알 수 있다. 조기에 출력 시작 못함. 

만약 매 초마다 1초분량의 데이터를 처리하고 싶다면? 혹은 이벤트 발생마다 처리하려면? 스트림 처리

스트림처리는 점진적 처리를 말한다. 일부 input에 대해서 뒤의 데이터 추가로 필요 없이도 output을 내보냄 

### 이벤트 스트림 전송 

- 이벤트는 문자열, JSON, 이진 형태로 encoding 후 처리된다. (네트워크에 전송가능한 형태로) 
- producer가 이벤트를 만들고, 복수의 consumer가 처리할 수 있다. topic이나 스트림으로 관련 이벤트를 묶어둔다. 

왜 DB에서 꺼내가게 하지 않는가? 

- DB를 폴링하게 하는건 오버헤드가 커지기 때문에. 새로운 이벤트도 없는데 계속 요청하게 됨 
- 이벤트가 나타날 때마다 소비자에게 알리는 방식이 유리 
- DB의 트리거 기능은 DB 설계할때 도입된게 아니라, DB 만들어진 다음에 추가된 기능중 하나. 알림 메커니즘으로 꼭 적합하진 않음 

#### 메시징 시스템 
보통 유닉스 파이프나, TCP 연결을 하는게 쉽다. 다만, producer나 consumer가 복수가 될 수가 없음.그래서 메시징 시스템이 나옴. 

webhook 같은것도 메시징 시스템이라 볼 수 있음. 단 publisher가 consumer로 직접 메시지를 전달하는 `직접 메시징 시스템`임.

메시지 브로커를 통해 메시지를 보내면 consistency 문제를 publisher나 consumer가 신경쓰지 않아도 된다. 복잡하게 큐잉, back pressure 같은걸 다 구현안해도 된다는 뜻. 

#### 복수의 소비자 

소비자를 많이두는 유즈케이스 두개

- load balancing. 메시지 처리가 비쌀 때 
- fan out. 여러 client가 받아야 할 때. 

로그방식 메시지 처리 방식: 토픽하나를 파티션 여러개로 가르고, 소비자 한 노드는 1개이상의 파티션을 전용으로 구독한다. 메시지 순서가 중요할때 좋다

JMS/AMQP 방식의 메시지 브로커: 메시지가 불변이고, 메시지 단위로 병렬화 처리하고 싶다면 

### DB에서 변경감지 할 수 있을까? 

색인 데이터가 안 만들어지더라도, 데이터 변경 요청이 왔을땐 빠르게 리턴해야 한다.

그래서 변경로그만 남기고 색인 데이터를 만드는데, 변경로그를 보고 동기화 하게 하려면, 원자적 커밋 문제를 풀어야 한다. A가 먼저 write되고 B가 그다음 write되는거 순서 역전 방지.

변경 데이터 캡쳐를 하자. 변경 데이터 캡쳐 (Change Data Capture) CDC는 변경사항을 캡쳐해서, 스트림으로 변경 내용을 내보내자는 것이다. 

Q. 어떻게 구현할까? 나같으면 들어오는 모든 SQL문을 이벤트로 내보낸다? 

로그 기반 메시지 브로커로 메시지 순서가 유지된채로 변경 이벤트를 전송한다. 

어떤 CDC는 스냅숏으로 주기적으로 메시지 offset에 맞춰서, 새로 들어온 소비자도 처음부터 메시지를 다 읽지 않고, 해당 스냅숏을 복사해가는 방법으로 더 최적화 했다. 

#### 로그 컴팩션
스냅숏말고, 같은 키값에 대한 변경건을 모아서 가장 최근값만 지니게 하고 있는거만 남기는것도 있다. 

같은 row에 대한 갱신이 많이 일어난 경우에 스냅숏보다 적합할수도? 스냅숏 만드는건 costly하니까 

### 이벤트 소싱 
어플리케이션 상태 변화를 이벤트 로그로 저장하자는 거다. CDC랑 차이는 추상화 정도의 차이. 

DB에서 변경 이벤트 추출하냐 VS application event의 로그를 추출하냐. (APP에서 일어난 일 저장)

예를들면, DB 2개에 변경을 가하는 회원가입 로직이있으면, 회원가입 이벤트가 일어났다가 DB 2개의 변경로그를 저장하는것보다 유리한셈 

#### 핵심
이벤트와 명령(command)를 구분해야한다. 사용자 요청 처음왔을때 명령이 온셈. 명령이 실패할 수도 있다. (unique key constraint 위반 등)

즉, 명령이 실행가능한지 판별한뒤 (무결성 검증) 명령이 승인되었을때 이벤트가 된다. (언제든 이 이벤트들을 쭉 되짚으면 현재의 어플리케이션 상태가 된다)

자기가 쓴 쓰기 읽기 문제도 해결할 수 있다. 자기가 쓴 쓰기 이벤트랑 읽기 이벤트가 같은 파티션에만 들어가게 되면 된다. 


### Command Query Responsibility Segregation - CQRS
- 데이터 쓰는 형식과 읽는 형식을 분리해두고, 다양한 읽기 뷰를 허용하면, 유연성을 얻을 수 있다.
- DB와 스키마 설계는 전통적으로 데이터가 질의를 받게 될 형식과 같은 형식으로 데이터를 기록하려고 한다. (이건 잘못됐대)
- 쓰기 최적화된 이벤트 로그에 담아두고, 다양한 read view를 만들어둔다면 상관이 없는 것. 읽기 최적화된 뷰는 데이터 비정규화 해둔게 합리적이잖아. 

### 윈도우 설계
- 처리시간 기반 윈도우를 설정하면 이 시간에 들어온 이벤트에 대해서 처리를 하겠다는건데, 이 경우 스트림의 지연이 요청률을 비대하게 만들 수 있음
- 이벤트 시간 기준 윈도우를 설정하면, 특정 윈도우에 지금 이벤트가 다 들어온건지 파악하기가 어려움. timeout 을 걸면 낙오자들을 파악가능한데. 두가지 해법 
  - 낙오자는 무시 
  - 수정값을 발행 

#### 윈도우 유형
- 텀블링 윈도우
  - 크기가 고정 길이 
    - 1분 텀블러 윈도우는 3분00초~ 3분 59초. 
- Hopping window
  - 고정 길이긴 한데, 윈도우를 중첩. 이전 이벤트도 포함시키는거
- Sliding window
  - 고정 시간이 아니라는 장점정도? 3분 39초 ~ 8분10초 이런이벤트를 같은 윈도우로 잡고싶다면 텀블링이나 hopping은 안돼.
- Session window
  - 고정 기간은 없는데, 30분동안 이벤트 비활성화되면 스킵
